TRAVEL APP

BUILD NEXT
[ ] 1. Support an existing plan without requiring generation.
    Add an 'Add my existing plan' entry point alongside the planner.
    Allow custom items such as flights, pickups, and personal activities,
    even when they have no matching Google place or known coordinates.

[ ] 2. Add practical trip and booking details.
    Store item date/time, destination time zone, address or meeting point,
    notes, booking reference, provider name, and contact details.
    Distinguish confirmed bookings from suggestions. Preserve fixed booking
    times when AI changes a schedule. Keep existing saved trips compatible.

[ ] 3. Import an itinerary from pasted text.
    Extract the supplied items into a draft daily schedule using AI.
    Let users correct and approve it before saving. Flag missing or unclear
    details instead of inventing booking references, times, or locations.
    Reuse the current itinerary editor, maps, and trip saving.

[ ] 4. Add a 'Today' view for a saved trip.
    Show today's items in time order, the next activity, and quick access
    to meeting points and booking details. Use the destination's local date.
    Let users browse other days when the trip is not currently underway.

[ ] 5. Add an 'Open directions' action for each located item.
    Reuse existing coordinates to open an external maps app.
    Ask users to add a location when one is missing.

[ ] 6. Validate the complete flow with real travelers.
    Try several actual itineraries: paste, review, edit, save, close,
    reopen, and find today's meeting point and booking details.
    Verify that older generated trips still restore correctly.
    Fix problems travelers encounter before expanding features.

LATER - AFTER THE CORE FLOW IS USEFUL
[ ] Import PDFs and booking screenshots.
[ ] Provide explicitly downloaded offline trip details and show sync status.
[ ] Share a trip with travel companions.
[ ] Add activity and transportation reminders.

DEFER
- Agent marketplace, agent dashboard, and direct booking integrations.
- Further AI planner expansion unless real user feedback calls for it.

SECURITY
[] 2. Move Cloud Functions off Node 20. Deprecated on 
      2026-04-30 and decommissioned on 2026-10-30 — roughly 
      seven weeks out. After that date you cannot deploy 
      functions at all until you upgrade. Do it on a calm 
      day, not the day you need to ship a fix.
      functions/package.json → "engines": { "node": "22" }
      deadline 30 oct

[] 3. Create the production Firestore database. It does not 
      exist yet, so rules cannot deploy there at all. The 
      location is permanent — asia-southeast1 (Singapore) 
      for a Vietnam-focused app. Start in locked mode so it 
      is never briefly world-writable.

[] 4. Deploy rules and indexes to production. Only after the 
      dev pass above is clean. Use the whole firestore target 
      so indexes go too, not just the rules.
      firebase.cmd deploy --only firestore --project travel-app-production-5e372

[] 5. Settle where the AI endpoint actually runs.
      The context cap only protects a deployed function. 
      Dev has no Secret Manager and no OPENAI_API_KEY, 
      which suggests dev uses the local Groq gateway — 
      in which case the cap is already live there and prod 
      is what needs deploying. Work out which, then deploy 
      that one.
      firebase.cmd functions:secrets:set OPENAI_API_KEY --project <project>

[] 6. Check the Google Maps/Places key is restricted. 
       That key ships inside the app and is readable by 
       anyone who has it. Unrestricted, it is another way for 
       someone to spend your money. Restrict by app and by API 
       in Google Cloud.


[] 7. Set the name under the app icon

      android/app/src/main/AndroidManifest.xml

[] 8. Decide on a domain
      About $10 a year, and it fixes the largest remaining 
      spam signal: mail from noreply@travel-app-production-5e372.firebaseapp.com. 
      Verification is a hard gate now, so an email lost to a spam folder is 
      a user who cannot get in at all. A sender name helps; 
      only a real domain plus custom SMTP fixes it.


[] 9. Settle the product name.
      It decides the app label, the email subject 
      line and the eventual store listing. The application 
      ID is already locked in as com.hungson.travelapp and 
      does not depend on this.


[] 10. Decide when to take on App Check
       Parked, and it is a project rather than a task: 
       Play Integrity on Android needs a SHA-256 fingerprint 
       and a Play Console link, DeviceCheck on iOS needs an 
       Apple Developer account, and web needs reCAPTCHA 
       Enterprise. It is the only thing that distinguishes 
       your app from a script holding a valid token — the 
       real protection for your OpenAI bill.

[] 11. Backfill ownerId onto old itineraries
       New itineraries carry it; older ones do not. 
       Once every document has it, the rules can drop the 
       per-document trip lookup, the queries can filter on 
       ownerId, and the 20-lookup ceiling — which breaks any 
       trip longer than about 20 saved days — goes away. 
       Needs a small admin script and a composite index.


[] 12. Rate-limit the AI endpoint per account
       Payload size is capped now; the number of calls is not. 
       One signed-in account can still loop the endpoint and 
       spend your model budget.


[] 13. Use a separate OpenAI key for dev.
       With its own spending limit set in the OpenAI dashboard. 
       Right now dev experiments and real usage bill the same 
       key with no way to tell them apart — and dev is where 
       the accidents happen.


[] 14. Require email_verified in the Firestore rules
       The app hard-gates on verification, but the rules do 
       not, so an unverified account can still reach the 
       REST API directly. Left out deliberately for now: 
       a stale token makes writes fail with 
       permission-denied even after the user has 
       verified, which is confusing to debug.


[] 15. Add tests for deletion and endpoint validation.
       The deletion cascade and the context cap are both 
       enforced by hand-checking today. The functions 
       suite covers place vetting only; nothing covers 
       interpretTripRequest's input validation or the 
       order the cascade deletes in.
